## ✅ Resolved: `./data` bind mount on `N:` caused a live crash (2026-08-02)

Originally discovered 2026-07-31 while verifying Phase 4 as a silent backup gap (see history below) — escalated to a real outage on 2026-08-02: the app crash-looped with `Bus error (core dumped)` right after the alembic migration step on every restart. Root-caused conclusively: a completely unrelated fresh container just opening `nekomail.db` with plain Python `sqlite3` reproduced the identical Bus error, while the exact same file copied to a local disk passed `PRAGMA integrity_check` clean (`ok`, 252 messages, 2 accounts intact — no data was lost). Network-mapped-drive bind mounts don't support the `mmap()` semantics SQLite's WAL mode relies on; Docker Desktop doesn't refuse this cleanly, it silently backs the mount with some internal store that eventually corrupts the mmap view.

**Fix applied**: moved the live data directory to `C:\NekoMailData` (local disk) and updated `docker-compose.yml`'s volume line accordingly. Confirmed stable afterward (clean startup, both accounts' IDLE watchers connected, no crash). **Do not point the `data` volume at a network-mapped drive again** — local disk only, matching what was already flagged below as the eventual fix when this was just a backup-blindspot concern.

## Status: Phase 2 complete — aioimaplib IDLE spike verified

Spike script at `backend/spikes/idle_spike.py`, run against a throwaway mailbox (`test123@nekos.farm`) on the mail.nekos.farm mailcow instance, IMAPS port 993 direct on the LAN (self-signed Dovecot cert — verification intentionally disabled in the spike only, never do that for user-supplied hosts in real account code). Confirmed:

- Login + SELECT work fine.
- IDLE delivers a real unsolicited `1 EXISTS` / `1 RECENT` push the moment new mail arrives (confirmed live, not just the periodic Dovecot "OK Still here" keepalive).
- `idle_done()` ends IDLE cleanly — the connection is immediately reusable for another command afterward.
- **Important finding for the sync engine (Phase 4):** a bare `asyncio.Task.cancel()` on the task returned by `idle_start()` does **not** safely end IDLE — it never sends the IMAP `DONE` line, so the server keeps thinking IDLE is active and the connection is left wedged (subsequent commands hang until forcibly closed). Any shutdown/reconnect path in the real sync manager must always call `idle_done()` explicitly (and await it) — never just cancel the task.

CRUD for mail Accounts under `/api/accounts`, Fernet-encrypted IMAP/SMTP credential storage, test-connect gating on create/credential-change, and RFC 6154 folder discovery. Verified end-to-end against the live `test123@nekos.farm` mailbox (create/list/get/patch/delete, bad-credential rejection with no partial persistence, folder discovery + re-discovery/update-in-place).

- **New models**: `Account` (`backend/app/models/account.py`) and `Folder` (`backend/app/models/folder.py`), migration `f8aee8285e02`. `Folder` only tracks discovery for now (name/delimiter/special_use/is_selectable) — sync-state columns (uidvalidity, last_seen_uid, backfill_watermark) get added onto it by a Phase 4 migration, not a new table.
- **Encryption**: new `database.EncryptedString` TypeDecorator (Fernet, same pattern as the existing `GUID` decorator) — `Account.imap_password`/`smtp_password` are ciphertext at rest, transparent to callers.
- **`imap_security`/`smtp_security`** are `"ssl" | "starttls" | "none"` (richer than NekoTicket's single boolean, deliberately — NekoMail must talk to arbitrary Gmail/Outlook/self-hosted servers, not one admin-configured server).
- **`Account.verify_ssl`** (default `True`) is a per-account opt-out for self-signed/private-CA IMAP certs, mirroring NekoTicket's `MailSettings.verify_ssl` — needed because this mailcow instance's Dovecot cert is self-signed even though its web UI cert isn't.
- **Real bug found and fixed**: `Account.updated_at` / `Folder.discovered_at` use `onupdate=func.now()` (server-computed). SQLite/aiosqlite eagerly fetches server defaults via `RETURNING` on INSERT, but not on UPDATE — leaves the attribute expired, which crashes response serialization with a `MissingGreenlet` error when accessed outside an awaited context. Fixed in `update_account` by calling `await db.refresh(account)` after `db.flush()`. Watch for this same trap anywhere else a flush is immediately followed by returning/serializing an updated (not freshly-`select()`-ed) ORM object.
- **Setup gap fixed**: `.env`'s `SECRET_KEY` and `MAIL_ENCRYPTION_KEY` were still the literal placeholders from `.env.example` (Phase 1 never exercised either — no encrypted columns existed yet, and itsdangerous doesn't validate key strength). Both are now real generated values. **Back up the current `.env`** — per its own header comment, losing `MAIL_ENCRYPTION_KEY` makes every stored account credential permanently undecryptable.
- **Operational note**: mailcow's fail2ban will briefly ban an IP after a deliberate bad-password auth attempt (observed firsthand while testing rejection behavior — a real login retried seconds later worked fine). Expected/correct server behavior, not a bug — don't build retry-around-it logic, just don't hammer bad credentials in a tight loop.

## Status: Phase 4a complete — poll-based core sync engine

Poll-based sync (connect → SELECT → fetch new/backfill mail → logout per call), triggered manually via `POST /api/accounts/{id}/sync`, no scheduler or IDLE/WebSocket push yet (that's Phase 4b, see below). Verified end-to-end against the live `test123@nekos.farm` mailbox: created a real Account + discovered its 6 folders via the existing Phase 3 endpoints, triggered sync, confirmed a real message landed as a `Message` row with correctly parsed subject/from/to/date/snippet/flags, its `.eml` written to `{mail_storage_path}/{account_id}/{folder_id}/{message.id}.eml`, and `Folder.uidvalidity`/`last_seen_uid`/`backfill_watermark` all set correctly across all 6 folders (only INBOX had mail). The test Account (`Test Mailbox`, `test123@nekos.farm`) was left in place in the DB for continued Phase 4 testing.

- **New files**: `services/mail/parser.py` (raw RFC822 bytes → structured fields via stdlib `email` + `policy.default`; HTML-only mail gets a crude regex tag-strip fallback for `body_text`/snippet since there's no `body_html` column — the full HTML is always still in the `.eml` for on-demand rendering later), `services/mail/sync.py` (the engine itself), `schemas/mail.py`, `services/message_service.py`, `routers/messages.py` (`GET /api/messages`, `GET /api/messages/{id}` — exists for verification now, will grow into the real mailbox API in Phase 5).
- **New config**: `MAIL_STORAGE_PATH` (default `./data/mail`, container path `/app/data/mail` set directly in `docker-compose.yml` — same `./data` bind mount as the DB, so no new volume needed). `eml_path` in the DB is stored **relative** to this root (host and container roots differ).
- **`probe.py`'s `_connect_imap` renamed to `connect_imap`** (dropped the leading underscore) since `sync.py` now shares it — it was already the right connect-with-security-mode logic, just needed to stop being private.
- **aioimaplib API gotcha hit while building this — record for next time**: `client.uid('search', ...)` raises (`UID only possible with COPY, FETCH, EXPUNGE, STORE`). Use the dedicated `client.uid_search(*criteria, charset=...)` method instead (pass `charset=None` to skip the `CHARSET utf-8` prefix it adds by default). `client.uid('fetch', ...)` and `client.uid('store'/'copy'/'move', ...)` are fine as-is.
- **Another aioimaplib gotcha**: `Response.lines` is *not* just the untagged data — for every command the **last** line is actually the tagged completion's status text (e.g. `b'Search completed (...)'`, `b'[READ-WRITE] Select completed (...)'`), appended after the real untagged data lines. For SEARCH, the actual UID/sequence list is `resp.lines[0]`, not `resp.lines[-1]`. (`_parse_folder_status` in `sync.py` sidesteps this by regex-scanning the whole joined blob instead of indexing a specific line.)
- **Single-UID fetches, not batched multi-UID literals**: `_fetch_range` does one `UID FETCH n (FLAGS RFC822)` round trip per message rather than a range fetch, to avoid ambiguous literal-boundary parsing across multiple messages in one response. Fine at personal-mailbox scale; revisit if a very large backfill is ever slow in practice.
- **UIDVALIDITY reconciliation** (`_reconcile_uidvalidity`) is implemented per the "don't blind wipe-and-resync" decision: on a UIDVALIDITY change it walks all current server UIDs, fetches just their Message-ID header, and remaps any locally-stored `Message.uid` whose `message_id_header` matches. It conservatively resets `backfill_watermark` to `0` (stops auto-backfill) on reconciliation, since the old watermark's UID numbering is now meaningless — not yet built: a way to manually restart a full backfill after this happens.
- **Initial-sync behavior**: first-ever sync of a folder fetches only the newest `INITIAL_BATCH` (200) messages, newest-first via descending UID range, and sets `backfill_watermark` to resume older mail from there; a large existing mailbox will need several sync calls (each backfills one more 200-message batch) before it's fully populated. There's no scheduler yet driving repeat calls — see Phase 4b.

## Status: Phase 4b complete — scheduler, dual-connection IDLE, WebSocket push

Phase 4 is now fully done. Verified end-to-end against the live `test123@nekos.farm` mailbox: sent a real email over SMTP, watched a connected WebSocket client receive `{"type": "new_mail", "account_id": ..., "folder_name": "INBOX", "new_count": 1}` within seconds via the IDLE push path (no manual `/sync` call). Also proved the reconnect/backoff logic under a **real** ~4-minute outage (mail.nekos.farm became unreachable on IMAP/SMTP/HTTP/SMTP-submission ports mid-session, almost certainly mailcow's fail2ban reacting to the burst of test connections made while building Phase 4a — 443 stayed open the whole time, so the host itself was up) — the watcher backed off cleanly (5s/15s/30s/60s/120s, capped) with no crash-loop, and reconnected within ~15s of the ports reopening, with zero manual intervention.

- **New files**: `services/ws_manager.py` (in-process `ConnectionManager` — single admin user, so broadcasts go to every connected client, no per-user routing), `routers/ws.py` (`GET /ws`, auth-gated via the existing `require_auth` dependency — FastAPI supports `Depends` on websocket routes the same as HTTP ones), `services/mail/scheduler.py` (everything below).
- **`main.py`** gained a `lifespan` context manager (`scheduler.start()` / `scheduler.stop()`) and `logging.basicConfig(level=logging.INFO)` so watcher connect/reconnect/error activity actually shows up in `docker compose logs`.
- **New config**: `POLL_INTERVAL_SECONDS` (default 300) for the full safety-net poll, `IDLE_RECONCILE_INTERVAL_SECONDS` (default 30) for how often the watcher set is reconciled against active Accounts.
- **Three concurrent pieces in `scheduler.py`**:
  1. `poll_loop()` — every `POLL_INTERVAL_SECONDS`, `sync_account()` on every active Account (all folders, not just INBOX — the thing IDLE alone wouldn't cover).
  2. `watch_account_idle(account_id)` — one dedicated IDLE connection per account on its INBOX only, using the exact `idle_start(timeout)`/`wait_server_push()`/`STOP_WAIT_SERVER_PUSH`/`idle_done()` pattern proven in the Phase 2 spike, refreshed every 25 minutes (under Dovecot's ~29-minute IDLE cap) via `idle_start`'s own built-in `call_later` timer. Reconnects with capped exponential backoff (5s→120s) on any failure. On a push containing an `EXISTS` line, triggers `_on_idle_push` which opens a **separate** fetch connection (never reuses the IDLE socket — Phase 2 finding) to sync just INBOX.
  3. `reconcile_idle_watchers()` — every `IDLE_RECONCILE_INTERVAL_SECONDS`, diffs active Accounts against running watcher tasks and starts/stops them; decouples account CRUD (`routers/accounts.py`) from the sync engine's internals.
- **Real concurrency bug found and fixed while verifying this**: the poll loop and an IDLE push can both react to the same new mail at once, each with its own DB session — both pass the "does this uid already exist" check before either commits, then race each other into the `(folder_id, uid)` unique constraint on insert (`sqlite3.IntegrityError`, reproduced live by sending mail and immediately firing concurrent manual syncs). Fixed by giving `sync_folder` (`services/mail/sync.py`) an in-process `asyncio.Lock` keyed by `(account_id, folder_id)`, and moving the commit/rollback *inside* `sync_folder` itself (it used to just `flush()` and let the caller commit later — outside the lock's scope, which didn't actually fix the race). All three call sites (poll loop, IDLE push, the manual `POST /accounts/{id}/sync` endpoint) now correctly serialize against each other per-folder while different folders/accounts still sync in parallel. Re-verified with 4 concurrent `sync_folder` calls against a folder with a genuinely new message: no errors, no duplicates.
- **aioimaplib gotcha**: `client.uid('search', ...)` doesn't exist for search (that's `client.uid_search(...)`, see Phase 4a notes above) — but the IDLE-relevant ones here are that `wait_server_push()` returns a raw `list[bytes]` of pushed lines (or the `STOP_WAIT_SERVER_PUSH` sentinel) directly, not a `Response` object, and `idle_start(timeout=...)` already schedules its own refresh timer internally (`self._idle_waiter = loop.call_later(timeout, ...)`) — no need to hand-roll a periodic re-idle loop, just consume the sentinel it produces.

- **Frontend**: hand-rolled fixed-row-height virtualized `MessageList` (no new dependency — mailbox sizes here don't warrant one), `ReadingPane` renders DOMPurify-sanitized HTML inside a **sandboxed `<iframe srcdoc>`** (`sandbox="allow-same-origin allow-popups"`, no `allow-scripts` — the sandbox is what actually blocks script execution, which is why inline `style=""`/`<style>` — very common in real HTML mail — didn't need to be stripped), with `cid:` inline-image references rewritten to the attachment-download endpoint. ## Status: Phase 6 complete — Compose & send

SMTP send, attachments, reply/reply-all/forward, Sent-folder append (skipped when `Account.auto_saves_sent` is true), draft autosave via replace-old-UID. Verified end-to-end against the live `test123@nekos.farm` mailbox via direct API calls (no browser tooling was available this session -- see "Not yet browser-tested" below): saved a draft, overwrote it (confirmed the old UID was gone from Drafts and only the new one remained), sent it with a real attachment to itself, confirmed the send actually delivered (arrived in INBOX, picked up live by the existing IDLE watcher), confirmed the draft was deleted from Drafts post-send, confirmed the Sent copy's attachment downloaded byte-exact, and sent a reply whose `thread_id` correctly matched the original (In-Reply-To/References wired up right).

- **Deliberately not a new DB table.** A draft is just a `Message` row that lives in the account's real Drafts folder, synced out exactly like any other mail -- "autosave" means APPEND a fresh copy to Drafts, then delete the previous version by its own uid. - **New files**: `services/mail/compose.py` (MIME building via stdlib `email.message.EmailMessage`, SMTP send via aiosmtplib, IMAP APPEND + resync via the existing `sync_folder`, draft replacement via STORE `\Deleted` + EXPUNGE -- same primitives `sync.py`/`actions.py` already established), `routers/compose.py` (`POST /api/messages/send`, `POST /api/messages/draft`, both multipart form endpoints so attachments can ride along with the text fields), `routers/contacts.py` (`GET /api/contacts?q=` -- the `Contact` model existed since Phase 4 purely for this, unused until now).
- **Renamed for cross-module reuse** (same precedent as Phase 4a/5's `_connect_imap`/`_lock_for_folder` renames): `actions.py`'s `_resolve_special_folder` → `resolve_special_folder`, now shared by `compose.py` to find each account's real Drafts/Sent folder.
- **Bcc is never written as a MIME header** -- only ever expands into SMTP envelope recipients (`aiosmtplib`'s `send_message(recipients=...)`), otherwise it wouldn't be blind. Confirmed by inspecting the sent message's stored headers.
- **Matching the newly-synced copy back to a `Message` row**: both send and draft-save generate their own `Message-ID` via `email.utils.make_msgid()` up front, then after the APPEND+resync (or, when `auto_saves_sent` is true, just a resync) look the row up by `message_id_header` match rather than "highest uid in the folder" -- avoids a race if something else touches the folder concurrently. ## Status: Phase 7 complete (code) — Outlook OAuth, not yet live-tested

MSAL Python public-client PKCE flow for linking Outlook/Microsoft 365 accounts. **Code-complete and regression-verified**, but **not yet tested against a real Microsoft account** -- that needs an actual Azure App Registration, which only the user can create (see setup steps below), plus a real Outlook mailbox to link. Regression-tested everything else this touched against the live `test123@nekos.farm` mailbox: IMAP IDLE watcher reconnected fine post-refactor, `test-connect` (both IMAP and SMTP) still passes, and a full compose/send round-trip still works. No errors in logs across any of it.

- **User decision this round**: after discussing that *any* Outlook support has to go through Microsoft's own auth one way or another (they killed IMAP/SMTP basic auth entirely), explicitly chose OAuth2/XOAUTH2 over IMAP (opt-in, bring-your-own Azure app per user) rather than ActiveSync -- EAS would actually be a *bigger* Microsoft dependency (proprietary protocol, historically license-encumbered, no mature open-source async Python library to build on) and a much larger lift, not a smaller one. NekoMail's core has zero Microsoft-specific code unless a user actually links an Outlook account.
- **Auth is not a new parallel system -- it's a branch inside the existing one.** `Account.auth_type` (`"password"` | `"oauth_outlook"`, immutable after creation) decides which of two things happens right before every IMAP/SMTP connection: LOGIN with the stored Fernet-encrypted password, or `AUTHENTICATE XOAUTH2` with a short-lived bearer token. Every single call site that used to build `ImapParams`/`SmtpParams` synchronously from `Account.imap_password`/`smtp_password` now goes through one shared, async, auth-aware resolver instead (`services/mail/account_conn.py::imap_params`/`smtp_params`) -- this touched `sync.py`, `actions.py`, `compose.py`, `scheduler.py`, and `account_service.py`. `services/mail/probe.py` gained `imap_login`/`smtp_login` helpers that branch on `params.auth_type`, replacing every direct `client.login(...)` call across the codebase.
- **New files**: `services/mail/outlook_oauth.py` (MSAL `PublicClientApplication` wrapper -- `start_flow`/`complete_flow`/`refresh`, all synchronous MSAL calls run through `asyncio.to_thread` so they don't block the event loop), `services/mail/oauth_token.py` (`get_access_token(db, account)` -- returns the cached token if still valid for >2 more minutes, otherwise refreshes via MSAL's refresh-token grant and persists the new access token, expiry, and possibly-rotated refresh token back onto the `Account` row), `services/mail/account_conn.py` (the shared resolver described above), `routers/oauth.py` (`GET /api/accounts/oauth/outlook/start` + `/callback`).
- **aioimaplib already had `xoauth2(user, token)` built in** (even links Microsoft's own OAuth-for-IMAP doc in its source) -- confirmed by inspecting the installed package before writing any code. **aiosmtplib has no XOAUTH2 support at all**, but exposes a low-level `execute_command()` -- built XOAUTH2 for SMTP by hand using the exact same SASL string format aioimaplib's own `xoauth2()` uses (`user=...\x01auth=Bearer ...\x01\x01`, base64-encoded -- RFC 7628 / the shared Microsoft+Google convention), sent as `AUTH XOAUTH2 <b64>` via `execute_command`.

## Status: Phase 8 complete — Rules & filters

Condition/action mail rules. All matching active rules fire (not first-match-wins), in `priority` order, and only ever against genuinely new incoming mail -- never retroactively over a folder's initial-sync batch or backfilled history. Verified end-to-end against the live `test123@nekos.farm` mailbox: created a rule (`subject contains "NEKORULE-MARKER"` → star + move to Junk), sent a real matching email, confirmed it got starred and moved out of INBOX into Junk **fully automatically via the live IDLE push path** (no manual sync involved), then confirmed a subsequent manual `/sync` with no new mail left every pre-existing message untouched (proving the not-retroactive design actually holds, not just in theory). Also verified rule PATCH (deactivate) and DELETE. No errors in logs across any of it.

- **Not a new DB table hanging off Message** -- `Rule` (`models/rule.py`, migration `3fc8cd9265eb`) is its own top-level table: `conditions`/`actions` are JSON columns (`[{field,operator,value}]` / `[{type,params}]`), `account_id` nullable (null = applies across every account under the user), `priority` (int, lower runs first) and `is_active`.
- **Where rules actually run is the interesting part**: `services/mail/rules.py::apply_rules_to_new_messages` is called by the three sync entry points (`scheduler.py`'s `poll_loop` and `_on_idle_push`, and the manual `POST /accounts/{id}/sync` endpoint) **after** `sync_folder`/`sync_account` has fully returned -- never from inside `sync.py` itself. Reason: `sync_folder` holds `lock_for_folder(account_id, folder_id)` for its whole pass, and a move/archive/trash rule action re-acquires that exact same (non-reentrant) `asyncio.Lock` via `actions.py` -- doing it from inside the sync would deadlock.
- **"Not retroactive" is enforced structurally, not by a flag.** `FolderSyncResult` gained `new_message_ids: list[int]` -- populated **only** by the forward-sync branch of `_sync_folder_locked` (the `highest > folder.last_seen_uid` path, i.e. mail that arrived since the last check). A folder's initial-sync batch and ordinary backfill both call the same `_fetch_range` helper (which now returns the new message ids instead of just a count) but their results are deliberately *not* threaded into `new_message_ids` -- so a brand-new account's first sync, or backfilling years of old mail, can never trigger a rule.
- **A rule with zero conditions matches nothing**, not everything -- `rule_matches` returns `False` outright rather than treating an empty condition list as "match all," to avoid an accidental blanket rule silently archiving/trashing every new email.
- **Known, documented limitation** (not a bug to fix, an inherent consequence of the move/archive/trash design from Phase 5): if two matching rules both try to move/archive/trash the *same* message, only the first one to actually execute has effect -- a move deletes the local row and lets the ordinary sync pipeline recreate it under a new id in its new folder (same mechanism `actions.py::_move_group` has used since Phase 5), so a second rule's action targeting the now-gone old id just no-ops via `actions.py`'s existing per-message "not found" error handling. Harmless, but worth knowing if two rules seem to only "half-apply."
- **New files**: `models/rule.py`, `schemas/rule.py`, `services/mail/rules.py` (CRUD + the condition-matching/action-execution engine in one module -- small enough not to warrant splitting), `routers/rules.py` (`GET/POST /api/rules`, `PATCH/DELETE /api/rules/{id}`).
- **Frontend**: `stores/rules.js` (plain CRUD, mirrors `accounts.js`), `views/RulesView.vue` -- a rule-list + inline add/edit form (same visual pattern as `AccountsView.vue`) with dynamic condition/action rows; picking "Move to folder" as an action requires the rule to be scoped to one specific account (not "All accounts") so a folder picker has something to populate from, enforced client-side before submit. ## Status: Phase 9 complete — PGP

Client-side-only PGP (openpgp.js): key generation/import, encrypt+sign combined into one PGP/MIME message, decrypt+verify, encrypt-to-self, encrypted attachments. **Live-verified the full crypto round trip against the real backend**, not just unit-level: wrote a Node script that reimplements exactly what the browser does (keygen, build a real PGP/MIME `multipart/encrypted` message, sign it), POSTed the resulting raw bytes through the actual `/api/messages/send` endpoint, confirmed it landed in Sent with `is_encrypted: true` and `snippet: null` / `body_text: null` (proving "search over encrypted mail is subject/sender only" holds structurally, not just by convention), fetched the ciphertext back out via the new `/api/messages/{id}/pgp` endpoint, decrypted it, and confirmed the body text and attachment came back byte-exact plus the signature verified correctly (and, as a negative check, correctly came back `false` when checked against the *wrong* public key, and `null` when no sender key was available at all -- proving verification isn't a silent no-op). No errors in backend logs across any of it.

- **The one hard requirement this phase had to actually deliver on**: "private keys never touch the server" only means something if the *entire* encryption operation happens client-side -- if the browser sent plaintext to the backend "to be encrypted there," the backend would see the plaintext regardless of who calls `encrypt()`. So the full RFC 3156 PGP/MIME structure (inner `multipart/mixed` entity with the text body + attachments, encrypted as one blob, wrapped in an outer `multipart/encrypted` with cleartext routing headers) is built entirely in the browser in `utils/pgpMime.js`, and the backend's `POST /api/messages/send`/`/draft` gained a `raw_mime` field that, when present, bypasses `build_mime()` entirely (`services/mail/compose.py`) -- the already-encrypted bytes are relayed as-is to SMTP (`aiosmtplib`'s low-level `sendmail(sender, recipients, raw_bytes)`, not `send_message()`) and to the IMAP Sent-folder APPEND. `to`/`cc`/`bcc` form fields are still submitted alongside `raw_mime` purely for SMTP envelope recipients (addresses aren't secret, only content is).
- **Real bug found and fixed while verifying this**: `openpgp.decrypt()`'s default `format: 'utf8'` *normalizes all line endings to bare `\n`* (documented behavior, not a bug in openpgp.js) -- but the browser-side inner-MIME re-parser (`splitMultipart` in `utils/pgpMime.js`) initially hardcoded `\r\n\r\n` as the header/body separator (correct for what gets *built*, since real MIME/SMTP transport requires CRLF) and silently returned empty-string bodies for everything after decryption, since the string it was actually searching just didn't contain `\r\n` anymore. Fixed by having the parser normalize to `\n` internally right up front and working entirely in that space -- caught immediately by the round-trip test, not something that would've surfaced from reading the code.
- **Where recipient public keys come from**: `Contact.pgp_public_key` (new nullable `Text` column, migration `de9333861ba7`) -- armored, stored in plaintext (public keys aren't secret, no `EncryptedString` needed, unlike every credential column on `Account`). Deliberately **not** automatic keyserver/WKD lookup (would mean silently trusting a third-party directory by default) -- the user pastes a contact's key in manually via the new `/pgp` settings view. New `GET /api/contacts/lookup?email=` (exact match) is what compose/reading use to check "does this address have a key on file"; the existing fuzzy `GET /api/contacts?q=` autocomplete search is unrelated to this.
- **Where the user's own key lives**: browser IndexedDB only (`utils/keyStore.js`, DB name `nekomail-pgp`), *never* the server -- meaning it's per-device by design, the same inherent limitation every browser-based PGP client has (Mailvelope etc.): set it up again on each device/browser you want to read encrypted mail from. The private key is always stored passphrase-encrypted (armored text straight from `openpgp.generateKey`); `stores/pgp.js` decrypts it into an in-memory-only `PrivateKey` object on `unlock()` that's cleared on `lock()`/page reload, never persisted decrypted anywhere. Importing an already-unencrypted private key is explicitly rejected (`pgp.importKeypair` checks `priv.isDecrypted()`).
- **Why `has_attachments`/the attachment-chip list look odd for encrypted mail, and why that's not a bug**: the backend's existing attachment detection (`parser.py`, unchanged since Phase 4a) walks the *outer*, unencrypted MIME structure -- for a PGP/MIME message that's just the `application/pgp-encrypted` version-marker part and the `application/octet-stream` ciphertext blob, so those show up as two meaningless "attachments" server-side. `ReadingPane.vue` now hides the normal attachment-chip row entirely when `message.is_encrypted`; the *real* attachments (the ones actually inside the encryption) only appear after a successful `Decrypt`, sourced from the client-side MIME split, downloaded via an in-browser `Blob`/object URL with no server round-trip needed (decryption already happened locally).
- **New endpoint**: `GET /api/messages/{id}/pgp` -- re-parses the stored `.eml` (same pattern as the existing `/html` and `/attachments/{id}` endpoints) and returns just the extracted armored ciphertext block (`parser.py::extract_pgp_ciphertext`, handles both PGP/MIME's `multipart/encrypted` and legacy inline `-----BEGIN PGP MESSAGE-----` for interop with older senders) -- offloads "find the ciphertext inside a real-world MIME structure" to Python's robust stdlib `email` parser instead of needing a JS MIME parser for the *outer* envelope.
- **Deliberately bounded v1 scope, not accidental gaps** (documented in `utils/pgpMime.js`'s own module docstring too): no sign-only `multipart/signed` mode (only combined encrypt+sign) -- a comparatively rare use case next to confidentiality; no Bcc on encrypted sends (a blind recipient would need their own separately-encrypted copy, which this version doesn't build -- the Bcc field is simply hidden in the compose UI while Encrypt is on); no automatic keyserver/WKD lookup (see above); the inner-MIME reader handles exactly the two shapes NekoMail's own compose flow produces (plain text, or one-level `multipart/mixed` with attachments) plus a plain-text fallback for anything more exotic a different PGP/MIME client might produce.
- **New files**: `frontend/src/utils/{keyStore,pgpMime}.js`, `stores/pgp.js`, `views/PgpSettingsView.vue` (own-key generate/import/export/delete/lock/unlock, plus contact-key management); backend `services/contact_service.py`, migration `de9333861ba7`. `openpgp@^6.3.1` added as a frontend dependency (the only "new dependency" exception this project has made outside the plan's own explicit call-out for this phase -- everything else has stayed hand-rolled).
- **Not browser-tested**: same caveat as Phases 5-8 (Chrome tooling unavailable this session) -- the compose Encrypt toggle, passphrase prompts, and the PGP settings UI's click-through are unverified beyond a clean production build. Given the crypto round trip itself is what actually carried risk here (get that wrong and it's a silent confidentiality failure, not a UI glitch) and *that* is thoroughly live-verified above via the real backend, this is a comparatively low-risk gap to leave for a manual pass.

## Key data-model gotchas already designed around (don't reintroduce these bugs)

- Raw `.eml` files on disk must be keyed by internal autoincrement `Message.id`, **not IMAP UID** — UIDs are only unique within `(account, folder, uidvalidity)` and collide across a UIDVALIDITY change otherwise.
- Initial sync fetches **newest UIDs first** (descending), batched 200-500 per `UID FETCH`, with a resumable `backfill_watermark` separate from the forward-sync `last_seen_uid`.
